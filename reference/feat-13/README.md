## RFD 6 ค้างไว้ · pack นี้ตัดสิน

`RFD 6 §3.2` ตั้งกฎของ Group D ว่า *ลบทิ้งทั้งตาราง แล้ว replay `chain_event`
ใหม่ ต้องได้ค่าเดิมเป๊ะ* และตั้งข้อสังเกตว่า `webhook_delivery` ทำแบบนั้นไม่ได้
จึงควรแยกเป็น Group E — **ยังไม่ตัดสิน**

ตัดสินว่า **แยก** และเหตุผลไม่ใช่เรื่องความสะดวก

1. ลบแล้ว replay **ไม่ได้แปลว่าได้ข้อมูลคืน** แต่แปลว่า **ยิง webhook
   ไปหาร้านใหม่ทั้งหมด** · นั่นเป็นผลข้างเคียงกับคนอื่น ไม่ใช่การสร้างตารางใหม่
2. ไม่มีค่าไหนในตารางนี้ที่สืบกลับไปหา `chain_event` ได้เลย
   `response_status` ที่ร้านตอบ · เวลาที่ยิงจริง · จำนวนครั้งที่ลอง
   chain ไม่รู้เรื่องพวกนี้ และจะไม่มีวันรู้

| กลุ่ม | คืออะไร | ลบแล้ว |
|---|---|---|
| Group D | projection · สืบจาก chain ได้ | สร้างใหม่ได้ |
| Group E | บันทึกการทำงาน · หลักฐานว่าเราทำอะไรไป | หายเลย |

สามตารางที่เป็น Group E ใน pack นี้ — `webhook_endpoint` `webhook_delivery`
`webhook_delivery_attempt` · **ห้ามใส่ในสคริปต์ที่ลบ Group D เพื่อสร้างใหม่**

T31 ตรวจด้วยการนับว่าไม่มี foreign key จากสามตารางนี้ไปหา `chain_event`
ถ้าวันหนึ่งมีคนเพิ่มเข้ามา ข้อสรุปนี้ต้องถูกทบทวน

## ข้อสำคัญที่สุดสำหรับคนเขียน client

**`status` ไม่เดินหน้าทางเดียว**

reorg ทำให้ `CONFIRMED` กลายเป็น `ORPHANED` ได้ ซึ่งดูเหมือนถอยหลัง
แต่ถูกต้องตามความจริงของ chain

```text
PENDING → SUBMITTED → CONFIRMED → ORPHANED → SUBMITTED → CONFIRMED → FINALIZED
seq 1        2            3           4          5           6            7
```

client ที่สมมติว่าสถานะเดินหน้าเสมอ แล้วทิ้ง event ที่ "ถอยหลัง"
จะทิ้ง event ที่สำคัญที่สุดไป — ตัวที่บอกว่างานที่คิดว่าเสร็จแล้วยังไม่เสร็จ

ใช้ **`eventSeq`** เทียบ · มันเพิ่มขึ้นเสมอ ไม่มีข้อยกเว้น
`isBackwardLooking()` ใน `types.ts` มีไว้ให้เห็นว่าข้อนี้คิดแล้ว ไม่ใช่ลืม

## ประวัติครบเสมอ · สามชั้น

`operation_event` คือสิ่งที่ client ควรอ่าน ไม่ใช่ `operation.status`
แต่ประวัติที่ขาดหรือโกหกก็ไร้ประโยชน์เท่ากัน จึงบังคับสามข้อ

| กฎ | กันอะไร |
|---|---|
| `seq` ต้องต่อจากแถวก่อนหน้าพอดี | ประวัติขาดช่วง |
| `from_status` ต้องตรงกับ `to_status` ของแถวก่อน | ประวัติโกหก |
| `trg_status_has_event` ตอน `COMMIT` | เปลี่ยนสถานะเงียบๆ ไม่เขียนประวัติ |

ข้อที่สามต้อง deferred เพราะลำดับการเขียนไม่แน่ — บางที่อัปเดต `operation` ก่อน
บางที่เขียน event ก่อน ทั้งสองแบบถูก ขอแค่ตอน `COMMIT` มันครบ

ผลที่ได้ตรงไปตรงมา

```text
UPDATE 1
ERROR:  operation o1 อยู่สถานะ SUBMITTED แต่ event แถวสุดท้ายจบที่ PENDING
HINT:  ทุกการเปลี่ยนสถานะต้องมีแถว operation_event รองรับ
```

T7 ตรวจทิศทางกลับด้วย — เขียน event โดยสถานะไม่เปลี่ยนก็ไม่ผ่าน
ประวัติที่เล่าเกินสิ่งที่เกิดขึ้น ก็ผิดเหมือนกัน

## webhook ของงานเดียวกันมาถึงเรียงตามลำดับ

`trg_delivery_order_gate` บังคับให้ delivery ลำดับก่อนหน้าจบ
(`SENT` หรือ `DEAD`) ก่อนจะยิงลำดับถัดไป ต่อหนึ่ง `(endpoint, operation)`

ทางที่ไม่เลือก — ส่งขนานกันแล้วให้ร้านเรียงเอง
**นั่นคือการย้ายปัญหาไปให้คนที่มีข้อมูลน้อยกว่าเรา** ร้านที่เขียนโค้ด
แบบตรงไปตรงมาจะเขียนสถานะทับด้วยค่าที่มาถึงทีหลัง ซึ่งผิดเมื่อมันมาสลับกัน

สองข้อที่ตามมา และทั้งคู่จำเป็น

- คิวของแต่ละ endpoint **แยกกัน** (T24) · ร้านที่รับไม่ได้ไม่ทำให้ร้านอื่นรอ
- `DEAD` **ไม่บล็อก** ลำดับถัดไป (T23) · รับไม่ได้ครั้งหนึ่ง ไม่ควรแปลว่า
  ไม่ได้รับอะไรอีกเลยตลอดกาล

## จบแล้วแก้ไม่ได้

`SENT` และ `DEAD` แก้ไม่ได้ และ `payload` กับ `signature` แก้ไม่ได้เลย
ตั้งแต่สร้าง · ตารางนี้เป็นหลักฐานว่าเราส่งอะไรไปและได้คำตอบอะไร
แก้ย้อนหลังได้ก็เลิกเป็นหลักฐาน

**การส่งซ้ำคือการสร้างแถวใหม่** ไม่ใช่การปลุกแถวเดิม
แถวใหม่ได้ `deliverySeq` ถัดไปของคิวนั้น และเซ็นใหม่ด้วยเวลาใหม่

## ลายเซ็นใส่เวลาเข้าไปด้วย

```text
X-Signature: sha256=<hex>
HMAC-SHA256(secret, "<signedAt>.<raw body>")
```

เซ็นแค่ body ไม่พอ — ใครที่ดักได้ครั้งหนึ่งจะส่งซ้ำได้ตลอดไป
ใส่ `signedAt` ในสิ่งที่เซ็น ร้านจึงปฏิเสธ body เก่าได้ (แนะนำ 5 นาที)

และตรวจจาก **byte ดิบ** ไม่ใช่จาก JSON ที่ parse แล้ว serialize ใหม่
`verifyWebhook()` ใน `status.service.ts` เป็นตัวอย่างที่เอาไปใช้ได้เลย
เทียบด้วย `timingSafeEqual`

### secret ไม่อยู่ในฐานข้อมูล

`webhook_endpoint.secret_ref` เก็บแค่ `kms://...` และ
`trg_endpoint_no_plain_secret` ปฏิเสธถ้าเผลอยัดค่าดิบลงไป (T15)
นี่คือ `L6` ในรูปของ webhook — ตาราง `wallet` ไม่มีคอลัมน์ private key
ตาราง `webhook_endpoint` ก็ไม่มีคอลัมน์ secret

API คืน `secret` **ครั้งเดียวตอนสร้าง** ลืมแล้วต้องหมุนใหม่ ไม่ใช่ขอดูอันเดิม

## บั๊กที่การทดสอบจับได้

T16 FAIL รอบแรก — `eventTypes` ที่เป็น array ว่างเล็ดลอดผ่าน `CHECK` ไปได้

```sql
-- ที่เขียนไว้ตอนแรก
CHECK (array_length(event_types, 1) >= 1)
```

`array_length(ARRAY[]::text[], 1)` คืน **`NULL`** ไม่ใช่ `0`
และ `CHECK` ที่ประเมินได้ `NULL` **ถือว่าผ่าน** (ล้มเฉพาะเมื่อได้ `FALSE`)
array ว่างจึงเข้าไปได้ และ endpoint นั้นจะไม่เคยได้รับ event อะไรเลย
โดยที่ร้านคิดว่าตั้งค่าไว้แล้ว

```sql
-- ที่แก้เป็น
CHECK (cardinality(event_types) >= 1
       AND array_position(event_types, NULL) IS NULL)
```

`cardinality` คืน `0` ให้ array ว่าง ซึ่งเป็นสิ่งที่ต้องการ
และเติมการกัน `NULL` ที่อยู่ในนั้นด้วย เพราะ `ARRAY[NULL]` มี cardinality 1
แต่ก็ไร้ประโยชน์เหมือนกัน

บทเรียน — ใน `CHECK` ทุกฟังก์ชันที่คืน `NULL` ได้ คือช่องว่างที่เปิดอยู่
`array_length` เป็นตัวที่เจอบ่อยที่สุดเพราะชื่อมันฟังดูปลอดภัย

## เรื่องที่เสียเวลาไปรอบหนึ่ง

**`SET CONSTRAINTS ALL IMMEDIATE` ไม่ใช่การตรวจครั้งเดียว**
มันเปลี่ยนโหมดไปจนจบ transaction · ไม่ตั้งกลับเป็น `DEFERRED`
ทุกการเขียนถัดไปจะถูกตรวจทีละสเตตเมนต์ ซึ่งผิดความหมายของกฎที่ออกแบบ
ให้ตรวจเป็นชุด และทำให้เทสต์ข้อถัดไปพังโดยไม่เกี่ยวกับสิ่งที่มันทดสอบ

และเอาสองสเตตเมนต์นี้ไปใส่ในฟังก์ชันแล้วเรียกจาก `DO` block ไม่ได้
จะได้ `stack depth limit exceeded` · จึงต้องเขียนตรงๆ ใน block

ข้อดีคือ ถ้า `IMMEDIATE` ระเบิด บรรทัดถัดไปไม่ได้รัน แต่ subtransaction
ของ `DO` block ที่จับ exception จะ rollback โหมดกลับให้เอง — ตรวจแล้วว่าจริง

**และบทเรียนเดิมจาก FEAT-12 ที่โผล่มาอีก** — `DO` block ที่คาดว่าจะ `raise`
จะ rollback ของที่มันสร้างเองไปด้วย ทำให้เทสต์ถัดไปเจอสถานะที่ไม่ได้ตั้งใจ
รอบนี้มันลามเป็นลูกโซ่ยาว กว่าจะเห็นต้นเหตุก็ไล่ย้อนไปสามข้อ
**ฉากต้องอยู่นอก block ที่อาจล้ม เสมอ**

## สิ่งที่ยังไม่ได้ตัดสิน

- **งานที่ค้าง `IN_FLIGHT`** เพราะ worker ตาย · ตอนนี้ `claimed_at` มีไว้ให้หาได้
  แต่ยังไม่มีตัวปล่อยคืนอัตโนมัติ · ต้องตอบว่ารอนานเท่าไรถึงถือว่าตาย
  และการปล่อยคืนจะทำให้ส่งซ้ำซึ่งร้านต้องรับได้
- **`PAUSED` endpoint** · ตอนนี้ไม่ตั้งคิวให้ แต่ยังไม่ได้ตอบว่า event
  ที่เกิดระหว่าง pause จะถูกส่งย้อนหลังเมื่อ resume หรือหายไปเลย
- **เพดานขนาด payload** และการตัด `response_body` ที่ร้านตอบกลับมา
  ตอนนี้เก็บทั้งก้อน ซึ่งร้านที่ตอบ HTML หน้า error ยาวๆ จะกินที่

## "ไม่มีวันมี" ในรูปของกลไก

`L6` เขียนว่าตาราง `wallet` ไม่มีคอลัมน์ private key **ไม่มีวันมี**

การไม่สร้างคอลัมน์นั้นวันนี้ ตอบได้แค่ครึ่งเดียว · อีกครึ่งคือกันคนที่จะเพิ่มมัน
ในอีกสองปี **ด้วยเจตนาดี** ตอนที่ไม่มีใครในทีมจำได้ว่าทำไมมันไม่มีตั้งแต่แรก

```sql
CREATE EVENT TRIGGER trg_no_secret_columns
  ON ddl_command_end
  WHEN TAG IN ('ALTER TABLE','CREATE TABLE')
  EXECUTE FUNCTION f_no_secret_columns();
```

```text
ERROR:  ห้ามมีคอลัมน์ private_key ในตาราง wallet (L6)
HINT:   key อยู่ใน KMS เท่านั้น · F10 และ F13 เกิดจากการเก็บ key ไว้เอง
```

ทำงานที่ชั้น DDL · ปฏิเสธทั้ง `ALTER TABLE` และ `CREATE TABLE`
และกัน **ทุกตารางในฐานข้อมูล** ไม่ใช่แค่ `wallet` (T9 สร้าง `wallet_backup_v2`
ที่มีคอลัมน์ `privkey` แล้วถูกปฏิเสธ)

T8 ตรวจชื่อสี่แบบ — `encrypted_key` `mnemonic` `sk` `seed_phrase` — ถูกปฏิเสธทั้งหมด

และ T10 ตรวจทิศทางกลับ · คอลัมน์ชื่อ `label` เพิ่มได้ปกติ
**กฎที่บล็อกทุกอย่างจะถูกปิดทิ้งในสัปดาห์แรก** จึงต้องพิสูจน์ว่ามันไม่กว้างเกิน

### ข้อจำกัดที่ต้องพูดให้ชัด

`CREATE EVENT TRIGGER` ต้องใช้สิทธิ์ superuser · migration มักรันด้วยสิทธิ์นั้น
แต่ถ้า production รัน migration ด้วย user ธรรมดา ข้อนี้จะไม่ถูกสร้าง
และ T7–T9 จะ FAIL เงียบๆ โดยไม่มีใครรู้ว่าการป้องกันหายไป

T12 จึงตรวจตรงๆ ว่า event trigger มีอยู่และเปิดใช้งาน **ไม่ใช่แค่หวังว่ามี**

และมันกันชื่อที่คิดไว้ ไม่ได้กันทุกวิธี · คนที่ตั้งใจเลี่ยงยังเลี่ยงได้
เป้าหมายคือทำให้**การเผลอ**เป็นไปไม่ได้ ไม่ใช่กันคนที่ตั้งใจ

## F6 · OTP ไม่ออกจาก server · กันสามชั้น

| ชั้น | กลไก | ทดสอบ |
|---|---|---|
| storage | ตาราง `otp_challenge` มีแต่ `code_hash` ไม่มีคอลัมน์เก็บ OTP | T4 |
| contract | `OtpChallengeAccepted` ไม่มีช่อง OTP และ `additionalProperties: false` | `contract-check.py` |
| compile | `interface OtpChallengeAccepted` ไม่มี field นั้น | `tsc` |

สามชั้นเพราะข้อนี้**เคยพลาดมาแล้วจริง** และคอมเมนต์ที่ติดมาคือ `// For testing purposes`
ซึ่งเป็นเหตุผลที่ฟังดูสมเหตุสมผลตอนเขียน

### ทำไมไม่ใช้ `sha256` เปล่า

`code_hash = HMAC-SHA256(pepper, challengeId || ':' || code)` โดย pepper อยู่ใน KMS

OTP หกหลักมีความเป็นไปได้แค่ **ล้านแบบ** · `sha256` ของทั้งล้านแบบ
คำนวณเสร็จในเสี้ยววินาที ใครได้ dump ฐานข้อมูลไปก็ย้อนหา OTP ได้ทุกแถว

pepper ที่อยู่นอกฐานข้อมูลทำให้การย้อนต้องได้ทั้งสองอย่าง

**ข้อควรระวัง** · `L7` / `SPEC-001 [IK-23]` ห้ามใช้ salt / secret / HMAC
แต่ข้อนั้นพูดถึง **fingerprint ของ idempotency key** เท่านั้น

| | ต้องการอะไร | เครื่องมือ |
|---|---|---|
| idempotency fingerprint | คำนวณซ้ำได้โดย**ไม่ต้องรู้**ความลับ | hash ตรงๆ |
| `code_hash` ของ OTP | คำนวณ**ไม่ได้**ถ้าไม่รู้ความลับ | HMAC |

เป้าหมายตรงข้ามกัน จึงใช้เครื่องมือต่างกัน · เป็นเรื่องเดียวกับลายเซ็น webhook
ใน FEAT-12 และ FEAT-13 · อ่าน `[IK-23]` กว้างเกินจะได้ OTP ที่ย้อนได้

## ลูกค้าไม่มีรหัสผ่าน

`F12` ใช้ `bcrypt(password,10)` · ที่นี่ตาราง `customer` ไม่มีคอลัมน์รหัสผ่านเลย (T32)

เหตุผล — รหัสผ่านในแอปที่ใช้เบอร์โทรเป็นหลัก สร้าง**ช่องทางกู้คืนเพิ่มอีกช่อง**
ซึ่งเป็นช่องที่โจมตีง่ายที่สุด และสุดท้ายการกู้คืนก็กลับมาที่ OTP อยู่ดี
จึงได้ความเสี่ยงเพิ่มโดยไม่ได้ความปลอดภัยเพิ่ม

`merchant_admin` ยังมีรหัสผ่าน (FEAT-03) เพราะคนละบริบท — คนที่เข้าหลังบ้านร้าน
ไม่ได้ถือเบอร์มือถือเครื่องเดียวกันเสมอ และมีหลายคนต่อร้าน

และ `F12` คืน `201` ไม่มี token ลูกค้าต้องไป login อีกรอบ · ที่นี่ยืนยันเสร็จ
คือเข้าสู่ระบบแล้ว (T33) · `customer_session` เก็บแต่ `token_hash` เหมือนที่
`otp_challenge` เก็บแต่ `code_hash` (T34)

## บั๊กที่การทดสอบจับได้ · และเป็นบั๊กเชิงแบบจำลอง

T21 FAIL ด้วย `violates check constraint "ck_ch_attempts"`

`f_verify_otp` เพิ่ม `attempts` ทุกครั้งที่ถูกเรียก รวมถึงครั้งที่ challenge
ถูกล็อกไปแล้ว · เมื่อ `attempts` ถึง `max_attempts` แล้วมีคนเรียกอีก
มันกลายเป็น 6 > 5 แล้ว `CHECK` พัง

แต่ปัญหาจริงลึกกว่าตัวเลข

> **`attempts` นับ "การเดา" ไม่ใช่ "การเรียก"**

เรียกตอน challenge ล็อกแล้ว **ไม่ใช่การเดา** — รหัสไม่ถูกเอามาเทียบเลย
นับเป็นการเดาคือการนับผิดความหมาย ไม่ใช่แค่ล้นขอบ

และตัวบันทึก `otp_attempt` ต้องเก็บ**ทุกการเรียก** เพราะคนที่ยิงรัว
ที่ challenge ที่ล็อกแล้วเป็นข้อมูลด้านความปลอดภัย · ทิ้งไปเงียบๆ
แปลว่ามีคนลองแล้วไม่มีใครรู้

จึงแยกสองความหมายออกจากกัน

```sql
-- เดิม · เทียบกับทุกแถว
SELECT count(*) FROM otp_attempt WHERE challenge_id = ...
-- แก้เป็น · เทียบกับแถวที่เป็นการเดาจริง
SELECT count(*) FROM otp_attempt
 WHERE challenge_id = ... AND result IN ('OK','WRONG_CODE')
```

T21b ตรวจข้อนี้ตรงๆ — ยิงรัว 3 ครั้งที่ challenge ที่ล็อกแล้ว
ได้ 9 แถวในตารางบันทึก แต่ `attempts` ยังเป็น 5

## ข้อจำกัดที่รู้อยู่

- **การเทียบ `code_hash` ใน Postgres ไม่ใช่ constant time** · `bytea =` ใช้ `memcmp`
  ยอมรับได้ที่นี่เพราะสิ่งที่เทียบคือ hash ไม่ใช่ OTP · คนที่วัดเวลาได้ก็ต้องเดา
  hash ที่มี 2^256 ความเป็นไปได้ และ `max_attempts` ตัดการวัดซ้ำที่จำเป็นไปแล้ว
  ถ้าวันหนึ่งต้องการ constant time จริง ต้องย้ายการเทียบไปที่โค้ด
  ซึ่งแลกมาด้วยการที่ hash ต้องออกจากฐานข้อมูล
- **event trigger กันชื่อที่คิดไว้ ไม่ได้กันทุกวิธี** · `jsonb` ที่ชื่อ `metadata`
  ใส่ key อะไรก็ได้ · คนที่ตั้งใจเลี่ยงยังเลี่ยงได้

## สิ่งที่ยังไม่ได้ตัดสิน

- **เปลี่ยนเบอร์** · ตอนนี้แก้ตรงๆ ไม่ได้ (T31) แต่ยังไม่มีเส้นทางที่ถูก
  ต้องตอบว่ายืนยันเบอร์ใหม่แล้วย้าย wallet หรือสร้างบัญชีใหม่
  และของที่ถืออยู่จะไปทางไหน
- **ลูกค้าที่ `PENDING_WALLET` ค้างนาน** เพราะ provision ล้ม · ตอนนี้เข้าแอปได้
  แต่รับของไม่ได้ และยังไม่มีตัวแจ้งเตือนหรือลองใหม่อัตโนมัติ
- **`ip_hash` ใน `otp_attempt` ใช้ทำอะไรต่อ** · เก็บแล้วแต่ยังไม่มีกฎที่อ่านมันไปใช้
  ถ้าจะทำ rate limit ต่อ IP ต้องตอบเรื่องคนที่อยู่หลัง NAT เดียวกันก่อน
- **เพดานต่อวัน** · ตอนนี้มีแต่ต่อชั่วโมง · คนที่ขอ 5 ครั้งทุกชั่วโมงทั้งวัน
  ยังทำได้ 120 ครั้ง ซึ่งน่าจะเกินที่ควร
- **OTP หกหลักพอไหม** · ล้านแบบกับ 5 ครั้งที่ลองได้ แปลว่าโอกาสเดาถูก
  1 ใน 200,000 ต่อ challenge · ยังไม่ได้ยืนยันกับฝ่าย risk ว่ารับได้

## feature นี้ปิดสองช่องที่อยู่ตรงข้ามกันพอดี

ข้างหนึ่งเงินไม่ไปถึง อีกข้างเงินงอกขึ้นมาเอง

| | ระบบเดิม | ที่นี่ |
|---|---|---|
| `F8` | `Vault.json` มี `lockFunds` `releaseFundsPartial` `returnFunds` ครบ · grep ทั้ง repo **ไม่เจอผู้เรียกเลย** | ทุกการเคลื่อนเงินเป็นแถวใน `ledger_entry` ที่ต้องรวมได้ศูนย์ |

ทั้งสองข้อแก้ด้วยกลไกเดียวกัน — **สมุดบัญชีคู่ที่ฐานข้อมูลบังคับให้สมดุล**

## สองกฎที่ตรวจตอน COMMIT

นี่คือส่วนที่ต่างจากทุก pack ก่อนหน้า

```sql
CREATE CONSTRAINT TRIGGER trg_ledger_balanced
  AFTER INSERT OR UPDATE ON ledger_entry
  DEFERRABLE INITIALLY DEFERRED ...     -- ผลรวมต่อ operation = 0

CREATE CONSTRAINT TRIGGER trg_balance_matches_ledger
  AFTER INSERT OR UPDATE ON thb_balance
  DEFERRABLE INITIALLY DEFERRED ...     -- ยอด = SUM(ledger ของบัญชีนั้น)
```

ต้อง deferred เพราะ **ชุดของ ledger ที่สมดุลมีความหมายเป็นชุด ไม่ใช่เป็นแถว**
แถวแรกที่เขียนลงไปจะไม่สมดุลเสมอ · ตรวจทีละแถวจึงเป็นไปไม่ได้

ผลที่ได้ตรงไปตรงมา — `INSERT` ผ่าน แต่ `COMMIT` ล้ม

```text
INSERT 0 1
ERROR:  ledger ของ operation op_v รวมได้ -500 ไม่ใช่ศูนย์
HINT:  เงินออกจากที่หนึ่งต้องเข้าอีกที่หนึ่งเสมอ

INSERT 0 1
ERROR:  ยอดของบัญชี CUSTOMER_THB:c1 เป็น 777 แต่ ledger รวมได้ 0
HINT:  ยอดคงเหลือเป็น projection ของ ledger ไม่ใช่ค่าที่ตั้งเองได้
```

ข้อความที่สองคือ `autoMintIfNeeded` ในรูปของ SQL · มันเขียนลงไปได้ แต่ commit ไม่ผ่าน

### บัญชี ISSUANCE

`ISSUANCE` เป็นบัญชีคู่ของการนำ THB เข้าระบบ · ยอดติดลบเป็นเรื่องปกติ
และเป็นบัญชีเดียวที่ `ck_balance_sign` อนุญาตให้ติดลบ

ค่าติดลบของมันเท่ากับ **THB ที่หมุนอยู่ในระบบทั้งหมด** — T17 ตรวจข้อนี้
ถ้ามีการเสกเงินสำเร็จที่ไหนก็ตาม สองข้างนี้จะไม่เท่ากัน

## กันเงิน ไม่ใช่ย้ายเงิน

ตอนรับคำขอ ระบบสร้าง `reservation` ของ `THB_BALANCE` เท่ายอดที่ต้องจ่าย
เงินยังอยู่ในบัญชีผู้ซื้อ · ยอดที่ใช้ได้ลดลงเท่านั้น · **ไม่มี ledger entry ใดๆ**

ผลคือทางกู้คืนว่างเปล่า — tx revert ก็แค่ปล่อยการจอง ไม่ต้องย้ายเงินกลับ
**ทางกู้คืนที่ว่างเปล่าคือทางกู้คืนที่ไม่พัง** และทางกู้คืนที่พังคือที่ที่ `F8` ตายไป

THB เป็นของบวกกันได้ ต่างจากคูปอง · `uq_reservation_exclusive` ใช้ไม่ได้
จึงล็อกด้วย `pg_advisory_xact_lock` ต่อบัญชี แล้วเทียบกับ `f_available_thb`
สองคำขอพร้อมกันเข้าคิวกัน ไม่ใช่ทั้งคู่อ่านยอดเดิมแล้วผ่านทั้งคู่ (`F1`)

| ของ | กลไก | เพราะ |
|---|---|---|
| คูปอง · listing · escrow | partial unique index | ของชิ้นเดียว จองซ้อนไม่ได้เลย |
| THB · point | advisory lock + คำนวณยอด | บวกกันได้ หลายคำขอแบ่งกันใช้ได้ |

## ขั้นที่สองเป็น tx เดียวโดยตั้งใจ

```text
1  approveTHB        อนุมัติเท่า totalPrice พอดี ไม่ใช่ไม่จำกัด
2  executePurchase   ย้ายทั้งเงินและคูปองใน tx เดียว · atomic
```

ถ้าแยกเงินกับของเป็นสอง tx จะเกิดสถานะ "จ่ายแล้วแต่ไม่ได้ของ"
ที่ต้องเขียนทางกู้คืน — และทางกู้คืนนั้นคือที่ที่ `F8` ตายไป
มีฟังก์ชัน `returnFunds` ครบ แต่ไม่มีใครเรียก

atomic บน chain จึงถูกกว่าทุกทาง · ไม่ต้องเขียนโค้ดที่ไม่มีใครรัน

## ค่าธรรมเนียม · ปัดลง และเศษตกเป็นของผู้ขาย

อัตราอยู่ในตาราง `fee_schedule` ที่มี `effective_from` ไม่ใช่ค่าคงที่ในโค้ด
`purchase.fee_bps` บันทึกอัตราที่ใช้จริงไว้กับแถวนั้น — เปลี่ยนอัตราวันนี้
ไม่ทำให้ยอดของการซื้อเมื่อวานเปลี่ยนตาม (T23)

`net` คำนวณจาก `total − fee` ไม่ใช่คำนวณแยกสองเส้น
ถ้าคำนวณแยกกัน ผลรวมจะขาดได้หนึ่งหน่วย และหน่วยนั้นจะหายไปจากระบบ
ซึ่ง `trg_ledger_balanced` จะไม่ยอม commit ให้ · กฎข้อหนึ่งบังคับอีกข้อ

ฐานข้อมูลตรวจเลขสามทาง ไม่ใช่สองทาง

```text
total = unit_price x quantity
fee + net = total                      ไม่ขาดไม่เกินแม้หนึ่งหน่วย
fee = div(total x fee_bps, 10000)      สูตรต้องตรงด้วย
```

T21 คือข้อที่พิสูจน์ว่าสามทางจำเป็น — ยอดรวมลงตัวแต่สูตรผิด ก็ยังถูกปฏิเสธ

## บั๊กที่เจอระหว่างทาง · ควรบันทึกไว้

รอบแรก T15 FAIL ด้วยข้อความ

```text
ยอดของ CUSTOMER_THB:cus_rich เป็น 1000e18 แต่ ledger รวมได้ 840e18
```

สาเหตุไม่ใช่ตัวเลขผิด แต่เป็นเรื่องที่ไม่ชัดเจนของ Postgres

> **`NEW` ของ constraint trigger ที่ DEFERRED คือค่าของแถว ณ ตอนที่สเตตเมนต์นั้นรัน ไม่ใช่ตอน COMMIT**

แถว `cus_rich` ถูกแก้สองครั้งใน transaction เดียว — ฝากเงิน แล้วจ่ายเงิน
จึงมี event สองตัวเข้าคิว · ตัวแรกถือ `NEW.amount` เป็นยอดหลังฝาก (1000)
พอถึง COMMIT มันเทียบ 1000 กับ ledger สุดท้าย (840) แล้ว raise
ทั้งที่สถานะจริงตอน COMMIT ถูกต้องสมบูรณ์

แก้โดย **ไม่ใช้ `NEW.amount` เลย** · อ่านค่าปัจจุบันจากตารางใหม่ใน trigger
ทำให้การตรวจเป็น "แถวตอนนี้ตรงกับ ledger ตอนนี้ไหม" ซึ่งเป็นสิ่งที่ต้องการจริง
และให้ผลเหมือนกันไม่ว่าจะมี event เข้าคิวกี่ตัว

บทเรียน — `NEW` ใน deferred trigger ใช้ได้เฉพาะกับช่องที่ไม่เปลี่ยน
(`account` `account_id` `operation_id`) ส่วนค่าที่สะสมต้องอ่านสดทุกครั้ง

## ข้อที่ต่างจาก data-model-v1

`data-model-v1` Group D มี `merchant_balance` · pack นี้ใช้ `thb_balance`
ที่คีย์ด้วย `(account, account_id)` แทน

เหตุผล — ใน marketplace **ลูกค้าก็ถือ THB** ไม่ใช่แค่ร้าน
และ platform ก็ต้องมีบัญชีรับค่าธรรมเนียม · สามบัญชีที่ทำงานเหมือนกันเป๊ะ
แยกเป็นสามตารางจะได้กฎที่ต้องเขียนซ้ำสามรอบ และ ledger ที่อ้างสามตาราง

ข้อนี้ควรแก้ใน `data-model-v1` · ยังไม่ได้แก้

## สิ่งที่ยังไม่ได้ตัดสิน

- ซื้อบางส่วนของรายการ · ตอนนี้ซื้อทั้งใบเท่านั้น
  ถ้าจะให้ซื้อบางส่วน ต้องตอบว่า `uq_purchase_listing` จะเปลี่ยนเป็นอะไร
  และคูปองที่เหลือยังอยู่ใน listing เดิมหรือแตกเป็นใบใหม่
- `PLATFORM_THB` ถอนออกจากระบบอย่างไร · ตอนนี้ยอดสะสมอยู่เฉยๆ
  การถอนต้องมีคู่บัญชีที่ไม่ใช่ `ISSUANCE` ไม่งั้น THB ในระบบจะไม่ตรง
- ค่าธรรมเนียมควรหักจากผู้ซื้อหรือผู้ขาย · ตอนนี้หักจากยอดที่ผู้ขายได้รับ
  ผู้ซื้อจ่ายเท่าราคาที่เห็น ซึ่งน่าจะถูก แต่ยังไม่ได้ยืนยันกับฝั่ง business
- `expectedTotalPrice` ควรเป็น required ไหม · ตอนนี้ required
  ทำให้ client ต้องอ่านราคาก่อนซื้อเสมอ ซึ่งเป็นภาระแต่กันความผิดพลาดได้

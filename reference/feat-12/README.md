## คำถามของ feature นี้

ไม่ใช่ "mint อย่างไร" แต่เป็น **"อะไรทำให้การ mint ครั้งหนึ่งถูกต้อง"**

`F4` — `autoMintIfNeeded` ของระบบเดิมเสก THB ด้วย admin key เมื่อยอดไม่พอ
ไม่มีเงินบาทจริงอยู่เบื้องหลัง และไม่มีใครรู้ว่าเสกไปเท่าไร

คำตอบที่นี่คือ trigger หนึ่งตัวที่ตรวจสามข้อในสเตตเมนต์เดียว

```text
trg_mint_requires_confirmed_deposit
  1  การฝากต้องอยู่สถานะ CONFIRMED          ← มีเงินบาทเข้ามาจริง
  2  ยอด mint ต้องเท่ากับยอดที่ฝากพอดี         ← ไม่มีส่วนต่างให้เสก
  3  ปลายทางต้องเป็นเจ้าของการฝากนั้น          ← เงินของใครก็ของคนนั้น
```

และ `thb_mint` มี primary key เป็น `deposit_id` — การฝากหนึ่งรายการ mint ได้ครั้งเดียว
ไม่ต้องเขียน trigger เพิ่ม ไม่ต้องสร้าง index เพิ่ม

## ISSUANCE ขยับได้ที่นี่เท่านั้น

`FEAT-10` ตั้งกฎว่าค่าติดลบของบัญชี `ISSUANCE` เท่ากับ THB ที่หมุนอยู่ในระบบทั้งหมด
กฎนั้นจะไม่มีความหมายเลยถ้า feature อื่นแตะ `ISSUANCE` ได้

```sql
CREATE TRIGGER trg_issuance_only_from_mint
  BEFORE INSERT OR UPDATE ON ledger_entry ...
  -- แถวที่ account = ISSUANCE ต้องมาจาก operation ที่ kind = THB_MINT
```

ผลคือเส้นแบ่งที่ชัด

| งาน | ทำอะไรกับเงิน |
|---|---|
| ซื้อขาย โอน (FEAT-05 · FEAT-10) | **เคลื่อนย้าย** ระหว่างบัญชี · ผลรวมไม่เปลี่ยน |
| FEAT-12 | **สร้างและทำลาย** · และต้องมีเงินบาทจริงรองรับทุกครั้ง |

T16 ทดสอบตรงๆ — `LISTING_BUY` เขียนแถวที่แตะ `ISSUANCE` แล้วถูกปฏิเสธ

## เงินเข้าธนาคาร กับ THB ปรากฏบน chain เป็นสองเรื่อง

ระบบเดิมรวมสองเรื่องเป็นเรื่องเดียว — ต้องใช้เงินก็ mint เลย
ที่นี่เป็นสองตาราง สองสถานะ และข้ามขั้นไม่ได้

```text
PENDING_PAYMENT → CONFIRMED → MINTED → REVERSED
                ↘ FAILED
                ↘ EXPIRED
```

`CONFIRMED` ต้องมี `webhook_id` อ้างอิง (`ck_dep_needs_webhook`) — ยืนยันเองลอยๆ ไม่ได้
ต้องมีคำพูดของผู้ให้บริการรองรับ

## Idempotency ของ feature นี้มาจากข้างนอก

ต่างจากทุก pack ที่ผ่านมา — ที่นี่เราไม่ได้เลือกคีย์ ผู้ให้บริการเลือก

| คีย์ | ใครเลือก | กันอะไร |
|---|---|---|
| `provider_event_id` | ผู้ให้บริการ | webhook ที่เขา retry |
| `provider_ref` | เรา ส่งให้เขา เขาส่งกลับ | การฝากซ้ำ |
| `Idempotency-Key` | client | `POST /v1/deposits` ที่ลูกค้าเรียก |

webhook ของผู้ให้บริการจะมาซ้ำแน่นอน — นั่นเป็นพฤติกรรมปกติของเขา ไม่ใช่ความผิดพลาด
`UNIQUE (provider, provider_event_id)` ทำให้มาซ้ำกี่รอบก็ประมวลผลครั้งเดียว

## ลายเซ็น webhook ใช้ HMAC และนั่นถูกต้อง

จุดที่อ่านผิดกันได้ง่าย — `L7` / `SPEC-001 [IK-23]` เขียนว่าห้ามใช้ salt / secret / HMAC

แต่ข้อนั้นพูดถึง **fingerprint ของ idempotency key** เท่านั้น
เพราะ fingerprint ต้องคำนวณซ้ำได้จากคำขอเดียวกัน โดยไม่ต้องรู้ความลับใด

ลายเซ็น webhook เป็นงานตรงกันข้าม — ต้องพิสูจน์ว่าผู้ส่งรู้ความลับ
HMAC คือเครื่องมือที่ถูกต้องสำหรับงานนั้น

**อ่าน `[IK-23]` กว้างเกินจะได้ webhook ที่ไม่ตรวจอะไรเลย** ซึ่งแย่กว่าเดิมมาก

สองรายละเอียดที่ตามมา

- ตรวจลายเซ็นจาก **body ดิบ** ก่อน parse · parse แล้ว serialize ใหม่ได้ byte คนละชุด และลายเซ็นจะไม่ตรง
- เทียบด้วย `timingSafeEqual` · การเทียบ string ธรรมดารั่วข้อมูลผ่านเวลา

### webhook ที่ลายเซ็นไม่ผ่านก็ยังบันทึก

ทิ้งไปเงียบๆ แปลว่ามีคนลองยิงเข้ามาแล้วไม่มีใครรู้ — นั่นคือข้อมูลด้านความปลอดภัยที่หายไป

แถวถูกเขียนพร้อม `signature_ok = false` และ `ix_psp_unprocessed` กรองออกจากคิวงาน
ที่ระดับ schema ไม่ใช่ที่ระดับโค้ด

```sql
CREATE INDEX ix_psp_unprocessed ON psp_webhook (received_at)
  WHERE processed_at IS NULL AND signature_ok;
```

## รอยต่อระหว่างเงินบาทกับ chain

สองหน่วย ตัวคูณคงที่ `10^16`

```text
1 สตางค์ = 10^16 base units
1 บาท    = 100 สตางค์ = 10^18 base units
```

นี่คือที่ที่บั๊กผิดหลักสิบยกกำลังอยู่ จึงไม่ปล่อยให้โค้ดคำนวณฝ่ายเดียว
`trg_deposit_amount_exact` คำนวณเองแล้วเทียบกับที่ส่งมา ทุกแถว ทุกครั้ง

`baseToSatang()` **โยน error เมื่อหารไม่ลงตัว** ไม่ปัดเศษ — ตัวเลขที่แปลงกลับไม่ได้
แปลว่ามันไม่ได้มาจากการฝากเงินบาท ซึ่งเป็นเรื่องผิดปกติที่ต้องรู้

## การตีกลับ · ส่วนที่ตอบยากที่สุด

เงินบาทถูกตีกลับ แต่ THB ถูก mint ไปแล้ว และอาจถูกใช้ซื้อของไปแล้ว
"ยกเลิก" ย้อนหลังไม่ได้ — ของที่ซื้อไปแล้วอยู่ในมือคนอื่น

| ยอดที่ใช้ได้ | ผล |
|---|---|
| ยังพอ | `BURNED` · เผา THB คืน · ledger สมดุล · จบ |
| ไม่พอ | `MANUAL_REVIEW` · ไม่แตะยอดเลย ไม่แต่งตัวเลข |

ทางที่ไม่เลือก และเหตุผล

| ทาง | ทำไมไม่เอา |
|---|---|
| ปล่อยยอดติดลบ | `ck_balance_sign` ไม่ยอม และยอดติดลบจะไหลไปทุกที่ที่อ่านยอด |
| เผาเท่าที่มี | ledger จะไม่สมดุล · ส่วนต่างหายไปเงียบๆ แบบ `F8` |
| เสกเงินมาเผา | คือ `F4` กลับหัว |

**ผลลัพธ์ไม่ใช่สิ่งที่โค้ดเลือก** — `available_at_reversal` บันทึกยอดที่ใช้ได้ตอนนั้นไว้
และ `trg_reversal_outcome_matches_balance` ปฏิเสธถ้า `outcome` ไม่ตรงกับยอดนั้น
**ทั้งสองทิศทาง**

- อ้าง `BURNED` ตอนยอดไม่พอ → `23514` (T22)
- อ้าง `MANUAL_REVIEW` ตอนยอดพอ → `23514` (T24)

ทิศทางที่สองสำคัญไม่น้อยกว่าทิศทางแรก · กันการเลี่ยงไปโยนให้คนตรวจทั้งที่เผาคืนได้

การยอมรับว่าบางกรณีต้องมีคนตัดสิน ถูกกว่าการแกล้งว่าแก้ได้อัตโนมัติ

## บั๊กที่การทดสอบจับได้ · และบั๊กนี้เป็นของจริง

T15 FAIL รอบแรก — "ยืนยันแล้วแก้ยอด → ถูกปฏิเสธ" กลับแก้ได้ฉลุย

สาเหตุอยู่ในลำดับของโค้ดใน trigger เอง

```sql
CREATE FUNCTION f_deposit_status_transition() ...
  IF OLD.status = NEW.status THEN RETURN NEW; END IF;   -- ← คืนค่าตรงนี้
  ...
  -- การตรวจว่าแก้ยอดไม่ได้ เขียนอยู่ตรงนี้ ใต้บรรทัดข้างบน
```

`UPDATE` ที่แก้แต่ยอดโดยไม่แตะสถานะ ทำให้ `OLD.status = NEW.status` เป็นจริง
ฟังก์ชันคืนค่าทันที และ **ข้ามการตรวจยอดไปทั้งหมด**

ยืนยัน 100 บาทแล้วแก้เป็น 1000 บาทได้ แล้ว mint 1000 — ซึ่งก็คือ `F4` อีกแบบ
เข้ามาทางประตูหลังที่ trigger เปิดไว้เอง

แก้โดยย้ายการตรวจยอดขึ้นไป **ก่อน** บรรทัดคืนค่า

บทเรียน — ใน trigger ที่มีการคืนค่าก่อนกำหนด ลำดับของกฎไม่ใช่เรื่องสไตล์
กฎที่ต้องใช้กับทุก `UPDATE` ต้องอยู่เหนือทุก early return และถ้ากฎนั้นไม่เกี่ยวกับ
สถานะเลย มันก็ไม่ควรอยู่ในฟังก์ชันชื่อ `..._status_transition` ตั้งแต่แรก

### อีกเรื่องที่ชัดขึ้นระหว่างเขียนเทสต์

T12 เดิมคาด `unique_violation` แต่ได้ `check_violation` — เพราะการ mint ซ้ำ
**ถูกกันสองชั้น** และชั้นสถานะยิงก่อน

| ชั้น | กลไก | กันกรณีไหน |
|---|---|---|
| 1 | สถานะ · mint แล้วเป็น `MINTED` ไม่ใช่ `CONFIRMED` | เส้นทางปกติ |
| 2 | primary key บน `deposit_id` | ยัดสองแถวใน transaction เดียวก่อนอัปเดตสถานะ |

จึงแยกเป็น T12 และ T12b เพื่อพิสูจน์ทั้งสองชั้นแยกกัน
ถ้าเขียนเทสต์เดียวที่รับทั้งสอง error จะไม่รู้ว่าชั้นที่สองทำงานจริงไหม

## สิ่งที่ยังไม่ได้ตัดสิน

- **ค่าธรรมเนียมของผู้ให้บริการ** · ตอนนี้ลูกค้าได้ THB เท่ายอดที่จ่าย
  และ platform รับภาระค่าธรรมเนียม PSP เอง นอก ledger นี้
  ถ้าจะหักจากลูกค้า ต้องตอบว่ายอดที่ mint คือยอดก่อนหรือหลังหัก
  และ `trg_mint_requires_confirmed_deposit` ข้อ 2 จะต้องเปลี่ยนตาม
- **`MANUAL_REVIEW` แล้วอย่างไรต่อ** · ตอนนี้บันทึกไว้แล้วรอคน
  ยังไม่มีเครื่องมือให้แอดมินตัดสิน และยังไม่ได้ตอบว่าใครรับภาระ
- **เพดานการฝาก** 20 ถึง 50,000 บาท เป็นค่าที่ตั้งไว้ก่อน ยังไม่ผ่านฝ่าย compliance
  และยังไม่มีเพดานรวมต่อวันต่อคน ซึ่งน่าจะต้องมี
- **`charge.complete` ที่ยอดไม่ตรง** · ตอนนี้บันทึกไว้แล้วไม่ยืนยัน
  ซึ่งทำให้การฝากค้างที่ `PENDING_PAYMENT` จนหมดอายุ ทั้งที่เงินเข้าแล้ว
  ต้องมีทางให้แอดมินเห็นและจัดการ
